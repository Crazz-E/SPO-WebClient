## 2. 🔴 P-C1 — Injection de trame RDO par texte non-Latin-1

**C'est le constat le plus grave de la passe, et il est reproductible.**

`src/server/rdo-helpers.ts:63` :
```ts
return socket.write(Buffer.from(frame, 'latin1'));
```
L'encodeur `latin1` de Node est une **troncature `charCode & 0xFF` sans caractère de remplacement**. Tout point de code dont l'octet de poids faible coïncide avec un métacaractère RDO est émis **comme ce métacaractère** — et cela se produit *après* l'échappement `"` → `""` de `RdoValue.format()` (`src/shared/rdo-types.ts:112`). **L'échappement ne peut donc rien protéger.**

**Reproduction (exécutée le 2026-08-14) :**
```
U+0122 Ģ -> 0x22 '"'        U+013B Ļ -> 0x3b ';'
U+012C Ĭ -> 0x2c ','        U+201C “ -> 0x1c (contrôle)

JS string  : C sel 8161308 call SayThis "*" "%hiĢ; C sel 1 call Evil Ģ*Ģ ";
SUR LE FIL : C sel 8161308 call SayThis "*" "%hi"; C sel 1 call Evil "*" ";
```
La seconde trame est une requête RDO **syntaxiquement valide**, dispatchée par `WinSockRDOConnectionsServer.pas:785-826` exactement comme une trame légitime.

**Accessibilité — confirmée.** `sendChatMessage` passe le texte utilisateur sans filtre : `args: [RdoValue.string('').format(), RdoValue.string(message).format()]` (`src/server/session/chat-handler.ts:166`). Idem sujet/corps de mail, noms de compagnie, termes de recherche, cookies. Une recherche de `charCodeAt|codePointAt|normalize(|sanitiz` sur tout `src/` ne remonte **que** de l'assainissement de chemins de fichiers dans `server.ts` — **aucun assainisseur de texte RDO n'existe**.

**Comportement de référence.** Le client legacy convertit WideString → AnsiString via `RDOUtils.pas:266-269` (`WideStrToStr`, donc `WideCharToMultiByte` sur la code page ANSI). Les points de code non mappables deviennent le **caractère par défaut `?`**. Le client de référence est *structurellement incapable* de placer `"` ou `;` sur le fil depuis une charge utile texte.

**Impact.** Désynchronisation de trame sur un serveur Delphi **de production partagé** ; au pire, injection de commande RDO arbitraire sur tout id d'objet que la passerelle connaît (`sel <ClientViewId> call …`). Un octet NUL issu d'une paire de substitution atterrit en prime dans une `AnsiString` Delphi.

**Correctif proposé (non appliqué).** Transcoder au point d'étranglement unique — dans `writeRdoFrame`, ou mieux dans `RdoValue.format()` : faire passer tout point de code > 0xFF par un encodeur Windows-1252 avec `?` en repli, **avant** quoting et échappement. Test unitaire asservi : `Ģ`, `Ļ`, `Ĭ`, `😀` doivent tous devenir `?`.

> **Note de priorité.** Tant que ce correctif n'est pas en place, la campagne de test live ne doit **pas** exercer la variante V2 (encodage) sur les champs texte — voir §6.

## 3. 🟠 P-H1 — `"^"` sur des procédures Delphi

**Nos octets** (3 sites) :
- `call AddLine "^" "%<ligne>"` — `src/server/session/mail-handler.ts:136-143`, `:229-236`
- `call CloseMessage "^" "#<id>"` — `mail-handler.ts:162-169`, `:255-262`
- `call SayThis "^" "%","%<msg>"` — `src/server/session/chat-handler.ts:160-167`

**Octets de référence** (capture) :
```
C 2174 sel 30430748 call AddLine "*" "%test message";   A2174 ;   [capture :3542-3543]
C 2177 sel 30437308 call CloseMessage "*" "#30430748";  A2177 ;   [capture :3548-3549]
```

**Règle de décision Delphi** — `Rdo/Client/RDOObjectProxy.pas:438-443` : le **séparateur** dépend uniquement du fait que le site d'appel consomme une valeur de retour ; le **QueryId** dépend de `fWaitForAnswer`. Ce sont deux axes **orthogonaux**. Avec `fWaitForAnswer = true`, un appel en position d'instruction sur une procédure donne **`"*"` AVEC QueryId** et un ack `A<id> ;` — exactement les trames capturées.

**Les trois membres sont bien déclarés `procedure`** ✅ vérifié directement :

| Membre | Déclaration | Fichier:ligne |
|---|---|---|
| `SayThis` | `procedure SayThis( Dest, Msg : widestring );` | `Interface Server/InterfaceServer.pas:179` |
| `AddLine` | `procedure AddLine(line : widestring);` | `Mail Server/MailServer.pas:140` |
| `CloseMessage` | `procedure CloseMessage(Id : integer);` | `Mail Server/MailServer.pas:112` |

**Le commentaire qui justifie notre `"^"` est faux** ✅ vérifié. `chat-handler.ts:159` affirme : *« Delphi `IClientView.SayThis` has an out ErrorCode param »*. Cette signature existe bien — mais dans **`Tests/3D Viewer/ClientView.pas:60`**, une unité de **test**. La variante `function … : OleVariant` de `Protocol/Protocol.pas:330` est **commentée**. Le serveur de production déclare une procédure nue à 2 arguments.

**Conséquence serveur.** `RDOQueryServer.pas:422-424` positionne `VType := varVariant`, donc `RDOObjectServer.pas:281-292` passe `@Res` en **argument caché supplémentaire**. Pour `AddLine`/`CloseMessage` (1 paramètre) il atterrit dans ECX et est ignoré. Pour **`SayThis` (2 paramètres), `RegsUsed` atteint `MaxRegs=3`, donc `push edi` empile un mot que la procédure appelée — convention `register`, sans paramètre pile — ne dépile jamais.**

**Sévérité.** Divergence de fil **prouvée** (le client de référence n'émet jamais cette forme) avec un mode de défaillance **[INFERRED]** (cf. U1 en §6). Pas de risque de double exécution : `spo_session.ts:2090-2091` exempte CALL/SET du retry.

**Inversion documentaire à corriger.** `doc/rdo-protocol-architecture.md` §8.5 ligne 2 interdit `QueryId + "*"` « par convention de projet » — or c'est **précisément la forme utilisée par le client de référence pour les membres void**, et la seule qui produise l'ack `A<id> ;` propre que la même section documente. La convention, telle qu'écrite, **pointe à l'opposé de la capture**. Le code suivant la doc, les deux doivent être corrigés dans la même passe.

## 4. 🟠 Autres divergences hautes

### P-H2 — Latin-1 vs Windows-1252
ISO-8859-1 et CP1252 coïncident sur 0xA0–0xFF (donc `é`, `ü`, `ñ` vont bien — le correctif A1/F1 était juste **là**) mais divergent totalement sur **0x80–0x9F**, qui en CP1252 porte les caractères les plus fréquents dans du texte collé : `€ … ' ' " " – — ™ œ`.
- Émission : `"` (U+201C) → `0x1C`, un octet de contrôle. Delphi enverrait `0x93`. ✅ vérifié.
- Réception : le serveur envoie `0x93` → nous décodons U+0093 (contrôle C1) → charabia à l'écran.
- `€` (U+20AC) → `0xAC` (`¬`) au lieu de `0x80`. ✅ vérifié.

Delphi passe par la code page ANSI du processus (`RDOUtils.pas:266-269, 283-286`), pas par ISO-8859-1. Impact : mojibake silencieux sur chat, mails, noms — les surfaces texte les plus fréquentes. Même point d'étranglement que P-C1 : **un seul codec CP1252 referme les deux**.

### P-H3 — Identifiants non validés
`src/shared/rdo-types.ts:409-413` et `src/server/rdo.ts:358-364` ne valident jamais le nom de membre. Chemin depuis le navigateur : `ws-handlers/building-handlers.ts:203-218` relaie `req.propertyName` tel quel → `building-property-handler.ts:147-150` (`set`) et `:169-174` (repli `call`, cf. M-D). Côté Delphi, `ReadIdent` (`RDOUtils.pas:70-78`) termine l'identifiant au premier caractère invalide et **le reste est parsé comme sous-commandes supplémentaires**. Un client navigateur peut donc invoquer une méthode publiée arbitraire, ou greffer une seconde requête, sur tout id d'objet que la passerelle détient.
**Correctif :** imposer `/^[A-Za-z_][A-Za-z0-9_]*$/` dans `RdoCommand.call/get/set` (invariant de couche protocole, pas d'affaire de handler) + liste blanche à la frontière WS.

### O-H1 — Session zombie après reconnexion légère
`login-handler.ts:979-1038` sonde la session avec `get TycoonId` sur l'**ancien** `ClientViewId`. Or côté Delphi, à la coupure : `TInterfaceServer.Logoff` fait `fClients.Extract(ClientView)` puis `fClientEventsProxy := Unassigned` — et **`//ClientView.Free;` est commenté** (`InterfaceServer.pas:3310-3326`). L'objet est donc **fuité mais vivant** : la sonde répond normalement, quasi toujours. On prend le chemin léger, et **plus aucun push n'arrivera** (l'IS itère `fClients`, dont nous avons été extraits) : la carte se charge, les bâtiments s'ouvrent, mais rien ne se met plus à jour et le joueur est invisible des autres. La passerelle, elle, annonce `EVENT_WORLD_RECONNECTED`.
Le legacy fait un **re-`Logon` complet à chaque fois** (`ServerCnxHandler.pas:3407-3473`).
**Correctif :** supprimer le chemin léger — sur `close` du socket monde, toujours `fullWorldRelogin`. Aucun membre publié ne permet de tester l'appartenance à `fClients`, donc aucune sonde moins chère n'est fiable.

### O-H2 — `RDOCnntId` périmé
Le chemin léger appelle `RegisterEventsById(ctx.rdoCnntId)` sur le **nouveau** socket avec l'id lu sur l'**ancien** (`login-handler.ts:998-1009`). Or cet id **est l'adresse mémoire de l'objet socket** (`WinSockRDOConnectionsServer.pas:664-668`). Cas attendu : pas de correspondance → AV capturée → `ERROR_CannotSetupEvents`, silencieux car le résultat est jeté (P-L1). Cas de queue **[INFERRED]** : le gestionnaire mémoire Delphi recycle l'adresse pour le socket d'un **autre** client, et nos pushes partent sur son fil. Correctif subsumé si O-H1 est corrigé.

### O-H3 — QueryId 0 ignoré
`spo_session.ts:2272` : `if (packet.type === 'REQUEST' && packet.rid)` — **`0` est falsy**. Deux lignes plus bas, la branche réponse fait correctement `packet.rid != null`. Or `0` est un QueryId réel et récurrent côté serveur : `GenerateQueryId` retourne **avant** d'incrémenter (`WinSockRDOServerClientConnection.pas:67-73`), donc `0` sort à la première requête push après redémarrage et à chaque bouclage sur 65536, **partagé par tous les clients**. Si la trame à rid 0 est l'`idof "InterfaceEvents"` émis à l'intérieur de `RegisterEventsById`, le serveur bloque 60 s, `InitClient` n'arrive jamais, et notre attente de 15 s échoue — un login qui rate pour ce qui ressemble à un problème réseau.
**Correctif :** `packet.rid !== undefined`. Une classe de caractères.

## 7. Angles morts des tests révélés par l'audit

Deux suites certifient des formes que la passerelle **n'émet pas** :
- `src/server/__tests__/rdo/login-flow.test.ts:94` asserte `/"[*^]" ;$/` — mais contre `src/server/__mocks__/mock-rdo-session.ts:103`, qui **code en dur** la chaîne legacy. `RdoCommand.build()` de production n'est jamais vérifié.
- `src/server/__tests__/protocol-validation/mail.validation.test.ts:133-152` construit à la main `separator: '"*"'` et l'asserte, alors que `mail-handler.ts` émet `"^"` — **P-H1 est donc invisible pour la suite**.

Tant que ces tests valident des paquets synthétiques plutôt que l'émission réelle, ils continueront de certifier des octets fictifs.

## 8. Ordre de traitement recommandé

1. **P-C1 → P-H2** — même point d'étranglement, un seul codec CP1252 referme les deux. **Priorité absolue** : c'est la seule faille exploitable depuis une saisie utilisateur.
2. **O-H3** — une classe de caractères, corrige un échec de login intermittent.
3. **P-H3 + validation des identifiants** — un contrat unique dans le constructeur de commandes.
4. **O-H1 (+ O-H2 subsumé)** — supprimer le chemin de reconnexion légère.
5. **M-B, M-E, M-C, M-D** — rendre les mutations vérifiables (lire les codes retour, liste blanche des membres). Sans cela, la campagne de test ne peut pas distinguer succès et échec silencieux.
6. **P-H1 + correction de la doc §8.5** — conditionné à la sonde U1.
7. Le lot MOYENNES/BASSES, et les deux angles morts de tests du §7 en même temps que P-L1.

> Les points 1 à 5 conditionnent la campagne live : tant que M-B/M-E tiennent, les oracles de la campagne sont aveugles sur une partie de la surface ; tant que P-C1 tient, la variante d'encodage (V2) ne doit pas être exercée en live.
