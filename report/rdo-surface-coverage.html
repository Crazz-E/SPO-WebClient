Why there are two legacy clients

The ASP pages are a second client, and the migration runs through here

Voyager was a shell around an embedded browser. A large part of what a player did — creating an account, subscribing, rating a mayor, setting a campaign project — happened on ASP pages served by the world, which opened their own RDO connection through Server.CreateObject("RDOClient.RDOObjectProxy") and called the model directly. Those pages are as much a source of truth as the Delphi client, and the WebClient is absorbing them one screen at a time.

What the ASP corpus adds

87 members that Voyager never touches at all. They cluster where you would expect the web to own the flow: account creation and directory keys (RDONewAccount, RDOCreateFullPathKey, RDOGetUserPath), subscriptions (RDODeleteFullPathNode, RDOReadDate), and tycoon finance (RDOAskLoan, RDOPayLoan, RDOSendMoney).

Six world instances ship the same pages, so each page counts once and is cited under Five/0/ — the instance the gateway fetches. 130 distinct pages are cited here.

The three members that started this

RDOSetRatingFrom, RDOSetPublicity and RDOSetProjectData were added to the catalogue from the Pascal declaration alone, with no client call site to copy — which looked like a hole in the evidence.

It was not. All three are ASP members: Visual/News/boardmsg.asp, Visual/Voyager/Politics/rdoModifyPub.asp and rdoModifyProject.asp. The Politics panel is the first ASP screen the WebClient absorbed outright, and this table now shows that lineage instead of an empty column.

Almost all of it is ASP work

Of the 41 remaining, the great majority are ASP-only. Account creation runs through Five/0/Visual/Voyager/NewLogon/rdoCreateAccount.asp (RDONewAccount, RDONewUserId, RDOCreateFullPathKey, RDOWriteString, RDOWriteInteger); the company selector is one page, NewLogon/chooseCompany.asp, which alone accounts for six GetCompany* members.

The whole subscription and billing branch — RDOGenSubscriptionId, RDOGenTransactionId, RDONotifyCharge, RDONotifyMoneyTransfer, RDORecordSubscriptionInfo — lives under Five/0/Subscription/ and talks to a payment gateway (callSIPS.asp, SIPSCallBack.asp). What is already wired, and what it costs to finish

The login path itself is done: RDOOpenSession → RDOLogonUser → RDOQueryKey / RDOSearchKey → RDOSetCurrentKey → Logon → TycoonId / AccountStatus → RDOEndSession. A player can sign in and enter a world.

What they cannot do is create an account, manage a subscription, or see more than the count of their companies — GetCompanyCount and NewCompany are wired, but every field the selector shows for each company (GetCompanyName, GetCompanyId, GetCompanyProfit, GetCompanyOwnerRole, GetCompanyCluster, GetCompanyFacilityCount) is not. That one page is the densest cluster of remaining work on this page.

Three catalogued members have no declaration — and all three are a different problem

A sweep of all 140 catalogued members against every procedure|function|property declaration in the ~1,750 .pas returns exactly these three — verified, not merely plausible: the supply siblings RDOSetInputSortMode, RDOSetInputMaxPrice, RDOConnectInput and RDOSetCompanyInputDemand all come back declared (Kernel/Kernel.pas:1077-1085, :1344), so the absence is real and not a grep artefact. Beyond the shared symptom they have nothing in common, and only one of them is a defect.

  1. Correct by design — RDOCnntId. Not a missing member: the query parser answers it before any object lookup and returns errNoError. tidConnRequestName = 'RDOCnntId' (Rdo/Server/RDOQueryServer.pas:9), intercepted at :269-274 with PropValue := IntToStr(ConnId). It reaches no class because it is answered by the connection, which is exactly what request-routing.ts documents. Nothing to fix.
  2. Never existed — RDOSetBuyingStatus. One occurrence in the whole legacy tree, and that call site is dead code. In Voyager/SupplySheetForm.pas:728-745, ObjId is declared at :731 and never assigned before Proxy.BindTo(ObjId) at :739 — where all four siblings in the same unit do ObjId := parms[0].vInteger and guard if (ObjId <> 0) (:642-644, :665-667, :688-690, :711-713). And threadedBuySet has no caller: it appears twice in the tree, its declaration at :162 and its body at :728. Voyager contains the call; it never emits it. So this is not a member the snapshot missed — it is a feature abandoned mid-write, and building-property-handler.ts:511 cites SupplySheetForm.pas line 741 as if it were evidence of emission.
  3. A real defect — RDOAutoRelease. The Pascal does not merely omit it; it shows why it cannot exist. The movie studio publishes exactly four members (StdBlocks/MovieStudios.pas:103-107), and auto-release travels as bit 0 of the AutoInfo : word argument of RDOLaunchMovie — flgAutoRelease = $01 at :19, read back at :494 and :693. The trailing comment on :104 still preserves the original signature where that parameter was named AutoRelease : WordBool. Voyager sets the bit at Voyager/FilmsSheet.pas:296-300 and emits it at :310, and nowhere else.

What that means for the Films tab. There is nothing to confirm against a live log — the declaration is the authority for a member's existence, and a log could only restate what :103-107 already settles. Two things are wrong today, and both are ours: the toggle is a silent no-op, because the WebClient sends it fire-and-forget (building-property-handler.ts:217-222) with no rid, so the server's errUnexistentMethod (Rdo/Common/ErrorCodes.pas:11, raised at Rdo/Server/RDOObjectServer.pas:326) is built and discarded for want of a destination; and the control should not be there at all — cbAutoRelease has no click handler in Voyager, only Enabled / Checked for display (FilmsSheet.pas:183, :194, :200), its value read once at :383 to feed the launch. Already known, partly. building-property-handler.test.ts:174-181 records the RDOAutoRelease finding under “NEW FINDING (lot 2)” with the same bitmask reasoning, but its citation is stale: it points at template-groups.ts:630, where the mapping is at :650 and the property row at :643. How this was built

Method, and what each column can be trusted to mean

The scope rule

962 .pas files were parsed for published sections inside class declarations — exactly what TRDOObjectServer can reach, via GetPropInfo for properties and GetMethodAddress for methods (Rdo/Server/RDOObjectServer.pas:90-200). That yields 760 members.

445 of them are then dropped, because no legacy client calls or names them. A member neither corpus reached is not a gap in the WebClient — it is protocol nobody used. What survives is the 315 rows here, including 7 the WebClient emits with no legacy trace, kept so our own surface is never under-counted.

Divergent forks are excluded by rule: unit paths resolve through the five server .dpr files, so Kernel.pas counts and Kernel0/1/2, Kernel.ok, Kernel.Iroel and Copy of Kernel do not.

What counts as Voyager using it

Called. Voyager binds late, through OleVariant proxies, so a call reads MSProxy.RDOSetTaxValue(TaxId, Value). Two detectors: every member reached through a variable declared : OleVariant, and every .RDO…( call regardless of receiver. 186 members.

Consumed. Voyager also reads properties by name, declared as string constants — tidInterest = 'Interest' in BankGeneralSheet.pas:17, then looked up on the cached property list. A string literal that exactly matches a published member name counts as consumption. 46 more members, shown as reads in the table.

The two are reported separately because they carry different weight: a call proves the wire traffic, a read proves only that the name mattered to a screen.

Reading the ASP corpus

ASP pages are VBScript, and the two objects they build are unambiguous. A variable assigned Server.CreateObject("RDOClient.RDOObjectProxy") is an RDO proxy — every member reached through it is a call, as is any .RDO… access regardless of receiver. A variable assigned Server.CreateObject("CacheManager.CachedObject") is a cache handle — members reached through it, and string literals matching a published name, are reads.

Same split as Voyager, same caveat: a read means the page displayed the value, not that it travelled over RDO. Five/fiveWS.asp and WebService/FiveWS.asmx are scanned too — the ASP.NET service that fronted account checks used the identical proxy. The bare Five/ template tree is skipped wherever Five/0 carries the same page, so a citation never lands on a near-copy.

The WebClient columns

Counted from real emission sites — rdoCall / rdoGet / rdoSet in src/server/, tests excluded. Eight of those sites dispatch a member chosen at runtime; each was expanded to the closed set it can actually name (KNOWN_RDO_COMMANDS, the world-property loop, the mail helpers, the gate-list spec).

The UI location is resolved from template-groups.ts where the member is a building-inspector command — that file maps every command to its tab and control — and is hand-attributed from the handler for session, map, mail, chat and politics paths.

Kind and the wire separator

The separator is not a style choice: a function takes ^ and a QueryId, a procedure takes * and none, a property is emitted as get / set with no separator at all.

Getting it wrong is not cosmetic. ^ on a procedure leaves a result pointer nobody pops (freeze); * on a function writes through a register nobody set (arbitrary memory write). This table reports the kind from the Pascal declaration, which is the only authority for it.

Counts are a census of the code as committed, not a claim about the live world. An ignored member may still be reachable — it simply has no caller in either legacy client. The scope grows as ASP screens are identified, so regenerate against current SPO-Original and SPO-ASP checkouts before treating any number here as final.
